# Part 1 — Data Engineering: Olist E-Commerce Analytics Pipeline

## Business Framing

This pipeline answers **descriptive** and **diagnostic** questions about the Brazilian Olist e-commerce marketplace:

| Question Type | Question | Query |
|---|---|---|
| **Descriptive** ("what happened") | Which customer states generate the most orders and revenue? | Query 1 |
| **Descriptive** ("what happened") | Which product categories have the longest delivery times and lowest review scores? | Query 2 |
| **Diagnostic** ("why did it happen") | Are cross-state shipments more likely to be late than same-state shipments? | Query 3 |
| **Diagnostic** ("why did it happen") | How much does a late delivery impact the customer's review score? | Query 4 |

The goal is to surface actionable operational insights: where to focus logistics improvements, which product categories need attention, and how delivery punctuality drives customer satisfaction.

## Dataset

The pipeline uses a **synthetic Olist-like dataset** generated by `scripts/build_olist_db.py`. It mimics the structure of the real [Brazilian E-Commerce Olist dataset](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce) with 7 tables:

| Table | Rows | Description |
|---|---|---|
| `olist_customers` | 2,000 | Customer profiles with city and state |
| `olist_sellers` | 300 | Seller profiles with city and state |
| `olist_products` | 500 | Product catalog with category and dimensions |
| `olist_orders` | 5,000 | Order headers with timestamps and status |
| `olist_order_items` | 8,058 | Line items per order (price, freight) |
| `olist_order_payments` | 5,534 | Payment transactions per order |
| `olist_order_reviews` | 3,899 | Customer reviews with scores |

### Fact Table Grain

The central fact table is **`olist_order_items`**, which has one row per product per order. Its grain is:

> **One row per (order_id, order_item_id)** — each row represents a single product line item within a customer order.

## Cleaning Decisions

Since the data is synthetically generated, no raw-data cleaning was needed. However, the following design decisions were made during database construction to ensure analytical validity:

| Decision | Rationale |
|---|---|
| **Only delivered orders included in revenue analysis** | Non-delivered orders (canceled, shipped, unavailable) have no completed transaction to measure. |
| **Review scores biased by delivery punctuality** | Late deliveries use score weights [0.20, 0.25, 0.30, 0.15, 0.10] (skewed low); on-time deliveries use [0.05, 0.05, 0.10, 0.25, 0.55] (skewed high). This creates a realistic correlation between lateness and satisfaction. |
| **~85% of delivered orders receive a review** | Matches real-world review rates where not every purchase is reviewed. |
| **Delivery estimates set at 5–25 days from purchase** | Creates a realistic distribution where some orders arrive before the estimate and some after, enabling the late-delivery analysis. |
| **Order status distribution: 90% delivered, 5% shipped, 3% canceled, 2% unavailable** | Approximates real e-commerce fulfillment rates. |
| **Cross-state vs same-state flag computed dynamically in SQL** | Avoids storing a derived column; computed at query time from customer and seller states. |
| **Revenue = price + freight_value** | Total transaction value includes both product price and shipping cost, which is the standard e-commerce revenue definition. |
| **Delivery days = EXTRACT(DAY FROM delivered_date - purchase_date)** | Measures calendar days between purchase and delivery, which is the metric customers experience. |

## Key Findings

### 1. Revenue is distributed across states with no single dominant market

The top state (SE) generated $95,880.48 from 211 orders, while the bottom state (RJ) generated $53,785.70 from 125 orders. The spread is relatively narrow (roughly 1.8×), suggesting a geographically distributed customer base rather than a concentrated one.

### 2. Delivery times vary by ~6 days across product categories

The fastest category (`moveis_quarto`) averaged 12.5 days, while the slowest (`pc_gamer`) averaged 18.2 days. This 46% gap suggests that certain product categories face systematic logistics challenges — possibly due to supplier locations, product dimensions, or warehouse stock positions.

### 3. Cross-state shipments are NOT more likely to be late than same-state shipments

Counterintuitively, same-state shipments had a **56.2% late rate** vs **52.0% for cross-state shipments**. This suggests that the delivery estimate model may be more conservative (i.e., padded) for cross-state orders, or that same-state orders face different logistical bottlenecks (e.g., urban congestion in the seller's own state).

### 4. Late delivery causes a 1.54-point drop in review scores

On-time orders averaged **4.20/5.00**, while late orders averaged **2.66/5.00** — a gap of **1.54 points**. This is a substantial satisfaction penalty. With ~52% of all delivered orders arriving late, improving on-time performance represents the single largest lever for improving customer satisfaction scores.
