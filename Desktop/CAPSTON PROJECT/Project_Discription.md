
Capstone Project — End-to-End Applied AI & ML Data Product
A mid-sized organization wants a small internal team to prove out a complete, production-style analytics workflow before committing budget to a full platform. You have been given a free choice of dataset and are asked to carry it through four independent stages: turn raw, messy data into a clean and query-able asset; turn that asset into a working predictive model; make the results usable by a non-technical audience through a live interactive dashboard; and, finally, add a large-language-model feature that turns unstructured text into reliable, structured information and answers free-form questions grounded in a document set.

Each of the four stages below is graded completely on its own. Treat each Part as a separate mini-project with its own repository: pick your inputs, write your code, and document your decisions inside that Part's own README.md. A grader will open each Part's submission independently and must be able to understand, run, and evaluate it without needing anything from any other Part. You are encouraged to reuse the same base dataset across Parts 1, 2, and 3 so that your work tells one coherent story, but this is a narrative choice, not a technical dependency — do not write code in one Part that imports files, models, or outputs committed only inside another Part's repository.

Descriptive, diagnostic, predictive, and prescriptive are the four broad questions any analytics product answers ("what happened", "why did it happen", "what will happen", "what should be done"). Keep these in mind as you write the framing/business-question sections asked for below — a strong submission is explicit about which of these questions each Part is answering.

One deliverable link per Part, no exceptions. The grading platform creates one question per Part and accepts exactly one submission link. Every Part in this project is a code deliverable, so every Part below asks for one public GitHub repository link. (For reference, the platform-wide convention used across this program is: code deliverables → one public GitHub repository link; non-code written deliverables, when a project has any, → one Google Doc link shared with "Anyone with the link can view" access before submission. This project has no text/Google-Doc Parts — all four Parts are code.)
Repository contents. Each repository must contain your code (notebook(s) and/or .py scripts), any small supporting files named in that Part's task list, and a README.md. The README.md is where all written explanation, justification, and discussion lives — there is no separate written-report deliverable.
Reproducibility. Every repository must run top-to-bottom from a clean environment using only the packages listed in a requirements.txt (or equivalent) at its root. State any API keys your code needs as named environment variables in the README (never commit an actual key).
No uploaded media of any kind. Nothing in this project is submitted as an image, screenshot, PDF, slide deck, presentation, video, or audio file. Charts and dashboards are code that produces visual output when it runs (inline notebook output, or a live deployed page) — they are never a separate upload. If you want to describe or justify a result in words, do so as text in the README.md.
Originality. All code, prompts, and written explanations must be your own work. You may consult official documentation for any library you use. Where you use an AI coding assistant to help write code, say so briefly in the relevant README — this is not penalized, but the understanding demonstrated in your README explanations must be your own.
Deadline. Submit all four Parts by the deadline announced for this assignment on the course portal/LMS. Late-policy, if any, follows the standard course policy.
